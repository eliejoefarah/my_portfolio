PostgreSQL DNA Extension

A C extension for PostgreSQL that adds native DNA sequence types with efficient bit-packed storage and a SP-GiST trie index — enabling typed DNA columns and index-accelerated k-mer queries directly in SQL.

CPostgreSQLDatabase InternalsSP-GiST

The Problem

PostgreSQL has no native DNA sequence type. Storing sequences as plain TEXT wastes 4× the memory (one byte per nucleotide instead of 2 bits), and k-mer substring queries require full-sequence scans with pattern matching. For bioinformatics workloads with large sequence tables, this is both slow and storage-heavy. The goal was to build a proper typed extension with compact storage and an index structure suited to the query patterns DNA data actually generates.

What I Built

Bit-Packed DNA Type

Each nucleotide is encoded in 2 bits (A=00, C=01, G=10, T=11), packing four bases per byte. The custom type implements PostgreSQL's varlena interface for variable-length storage, with input/output functions that handle ASCII ↔ bit-packed conversion transparently.

SP-GiST Trie Index

The index is built on PostgreSQL's SP-GiST framework, which supports space-partitioning strategies — a natural fit for trie structures. The trie branches on 2-bit nucleotide values, enabling prefix-based k-mer lookups with O(k) traversal rather than O(n) full scans.

screenshot: EXPLAIN ANALYZE with index scan
[root] / | \ \ A C G T /| | \ AA AC CA GT ... Each path from root → leaf encodes a k-mer prefix. A query for sequences containing "ACG" traverses 3 levels rather than scanning every row.

SP-GiST vs GiST — Why It Matters Here

PostgreSQL offers both GiST (Generalized Search Tree) and SP-GiST (Space-Partitioned GiST) for custom index types. GiST is balanced and general — it works by choosing arbitrary pivot points and splitting data around them. SP-GiST is designed for structures where the space itself has a natural partition, like tries or k-d trees.

DNA sequences share common prefixes — that's precisely the structure a trie exploits. Using GiST here would force balancing across arbitrary pivot points that don't correspond to meaningful sequence boundaries. SP-GiST lets the trie branch naturally on nucleotide values, producing a tree where each traversal step eliminates 3/4 of the remaining candidates at each nucleotide position.

What I'd Do Differently

The current implementation handles exact k-mer matching well, but bioinformatics queries often need approximate matching — sequences with up to k substitutions or insertions. Adding edit-distance operators with a bounded-search trie traversal would make the extension genuinely useful for alignment tasks. I'd also add GIN-based k-mer inverted indexes as an alternative for workloads that favor bulk containment queries over prefix lookups.
